# A09 — Hunter Stalker (core-rulebook.txt lines 2795–3055, pages 62–67)

Scope: Core Hunter Stalker Traits table, the level 1–20 Features table, all class
feature descriptions, Cunning Strike / Devious Strikes options, and the Assassin
and Shadow subclasses. Compared against `src/data/classes.ts` (`stalker` entry),
`src/features/hunter/lib/characterAutomation.ts`,
`src/features/hunter/components/papersheet/CharacterAutomationProvider.tsx`,
`src/features/hunter/components/character-sheet/upgradeModel.ts` +
`CharacterSheetUpgrade*.tsx`, `src/features/hunter/components/appsheet/AppClassAbilities.tsx`,
`src/data/abilities.ts`, `src/data/feats.ts`.

**Overall:** the Stalker entry is a very close match. The core traits, the full
20-level table (Proficiency Bonus and Sneak Attack columns), every class feature
text, and both subclasses' features are verbatim-equivalent to the txt. The
findings below are the real deltas.

### Subclass list in the level-3 feature text still says "Thief"
- **txt_section**: core-rulebook.txt [page 64] "LEVEL 3: HUNTER STALKER SUBCLASS" (line 2886–2893): "The Assassin or the Shadow subclasses are detailed after this class's description." Confirmed by [page 66] line 2975–2982: "This section presents the Assassin and the Shadow subclasses."
- **rule_summary**: The two Stalker subclasses are **Assassin** and **Shadow**. There is no "Thief" subclass anywhere in the beta text.
- **code_location**: `src/data/classes.ts` line 229 — `features[]` entry `{ level: 3, name: "Hunter Stalker Subclass", text: "... The Assassin or the Thief subclasses are detailed ..." }`. (The actual `subclasses[]` array at lines 242–268 is already correct: `assassin` + `shadow`.)
- **verdict**: mismatch
- **proposed_change**: In that one string, replace `the Thief subclasses` with `the Shadow subclasses`. Text-only; the subclass data itself needs no change.
- **stored_data_impact**: none for the catalog. Saved cards store `subclassId`; no card can hold `"thief"` because the array never offered it. But `sheet.features1` is a materialised snapshot produced by `featureText()` in `characterAutomation.ts`, so existing `/characters/{id}` records of Stalkers level ≥3 contain the stale "Thief" sentence — it is regenerated by `calculatedSheetFields()` on the next save, unless `features1` is in `sheetAutomation.manualOverrides`.

### Starting equipment omits the Cavalier Hat
- **txt_section**: core-rulebook.txt [page 63] Core Hunter Stalker Traits, "Starting Equipment" (lines 2826–2830): "Scimitar, 4 Daggers, Pistol, Bullets (5), Toolbelt, Ankle Holster and Thieves Tools, **Cavalier Hat**".
- **rule_summary**: The Stalker's starting kit has eight entries; the eighth is a Cavalier Hat. The item exists in the equipment tables: [page ~40] line 1780 "Cavalier Hat  Extra: Head  0  1 lb.  Is given by class."
- **code_location**: `src/data/classes.ts` line 198 — `startingEquipment: ["Scimitar", "4 Daggers", "Pistol", "5 bullets", "Tool Belt", "Ankle Holster", "Thieves' Tools"]` (7 entries, no hat). The item does exist in the app as armor: `src/data/armor.ts` lines 154–155, `id: "cavalier-hat"`.
- **verdict**: missing_in_code
- **proposed_change**: Add `"Cavalier Hat"` to the Stalker's `startingEquipment`. Note the plumbing: `startingKit()` in `src/lib/startingEquipment.ts` resolves names only against `ITEMS` (`src/data/items.ts`), and the Cavalier Hat lives in `ARMOR`, not `ITEMS` — so a bare string addition would fall into `unmatched` rather than granting the hat. The minimal correct fix is to let the starting-kit resolver also match `ARMOR` head-gear ids and seed `extraArmorIds`, or to grant `cavalier-hat` via an explicit `startingArmor` field. (The Scout has the same omission — core-rulebook.txt line 2492 — so fix it once in the resolver, not per class.)
- **stored_data_impact**: Existing Stalker cards were built without the hat. Backfill is optional and player-visible (it changes the `headGear` sheet field and adds 1 lb of carried weight). Safer: no retroactive backfill; new characters only.

### Mastery-weapon picker for the Stalker is a hardcoded list that contradicts the proficiency rule
- **txt_section**: core-rulebook.txt [page 63] "Weapon Proficiencies: Simple weapons and Martial weapons that have the Finesse or Light property" (lines 2817–2820), plus the weapon table [page ~110] lines 5000–5033 and "LEVEL 2: WEAPON MASTERY" (line 2836–2840): mastery may be chosen from "two kinds of weapons of your choice **with which you have proficiency**".
- **rule_summary**: A Stalker is proficient with every **Simple** weapon — Club, Dagger, Greatclub, Handaxe, Javelin, Light Hammer, Mace, Sickle, Spear, Throwing Knife — plus **Martial** weapons with Finesse or Light: Rapier, Scimitar, Shortsword, Whip. **Pistol is Martial Ranged with properties "Ammunition (30/90; Bullet)" only — no Finesse, no Light — so the Stalker is *not* proficient with it** (it is still handed out as starting gear, which is a separate thing), and Hunter Rifle likewise.
- **code_location**: `src/features/hunter/components/papersheet/CharacterAutomationProvider.tsx` lines 174–182 — `const finesseOrLightIds = new Set(["shortsword", "scimitar", "sickle", "handaxe", "dagger", "pistol"])`, used as `if (klass?.id === "stalker") return finesseOrLightIds.has(item.id)`.
- **verdict**: mismatch
- **proposed_change**: Remove `"pistol"` from `finesseOrLightIds`, and add the missing eligible weapons that exist in `src/data/items.ts` (at minimum Club/Greatclub/Javelin/Light Hammer/Mace/Spear/Throwing Knife/Rapier/Whip, for whichever are catalogued). Properly: `src/data/items.ts` weapon entries carry no `properties`/`category` (Simple vs Martial) data at all — adding those two fields from the txt weapon table (lines 5000–5033) would let this filter be derived rather than hardcoded, and would also fix the parallel hardcoded `meleeWeaponIds` set on line 170.
- **stored_data_impact**: `sheetAutomation.weaponMasteries` on existing Stalker cards may contain `"Pistol"`, which would become an invalid selection. On load, filter stored masteries against the eligible list and surface the freed pick through the existing `pending`/upgrade flow rather than silently dropping it.

### Slippery Mind's Wisdom/Charisma save proficiency is never applied to the sheet
- **txt_section**: core-rulebook.txt [page 65] "LEVEL 15: SLIPPERY MIND" (lines 2941, 2949–2950): "You gain proficiency in Wisdom and Charisma saving throws."
- **rule_summary**: From Stalker level 15 the character is proficient in **four** saving throws: Dexterity and Intelligence (core traits, line 2808–2809) plus Wisdom and Charisma.
- **code_location**: `src/features/hunter/lib/characterAutomation.ts` lines 199–207 — `const saveProficient = klass?.savingThrows.includes(key) ?? false;` sets both `{key}SaveP` (the checkbox) and `{key}Save` (the number) purely from the static `klass.savingThrows` array (`["dex","int"]`, `src/data/classes.ts` line 189). No level-15 adjustment exists anywhere.
- **verdict**: missing_in_code
- **proposed_change**: In `automationFor`, derive the save-proficiency set as `klass.savingThrows` plus, for `classId === "stalker" && level >= 15`, `"wis"` and `"cha"` — mirroring how `featNames.has("Tough")` etc. already adjust derived values in the same function. Reuse the existing `reasons` string ("Slippery Mind at Hunter Stalker level 15") so the sheet's why-tooltip still explains it.
- **stored_data_impact**: Level 15+ Stalker cards currently store `wisSaveP`/`chaSaveP` as `false` and understated `wisSave`/`chaSave` values in `sheet`. These are recomputed by `calculatedSheetFields()` on the next save; no field needs stripping, but any of these four keys present in `sheetAutomation.manualOverrides` will keep the wrong value.
